Lesson 0004 — Tenant isolation

Primary source: OWASP "Multi-Tenant Architecture" + Helix's tenant-isolated memory design.

Why this lesson

Multi-tenant SaaS (or multi-campaign centres) means one system serves many customers. Tenant isolation is the guarantee that tenant A's data, actions and failures never leak into tenant B's. A breach here is not a bug — it's a contract violation.

Concept

  • Shared infrastructure, isolated data. One codebase, one DB cluster, but data partitioned by tenant key on every query.
  • Tenant context in the request. Every request carries a tenant id; the data layer enforces it, not the app code (defence in depth).
  • No cross-tenant reads/writes. A query without a tenant filter is a bug, not a feature.
  • Per-tenant limits. Rate limits, storage, concurrency scoped per tenant so one tenant can't starve others.

Helix uses tenant-isolated governed memory with retention, per-request correlation IDs, and a demo role deliberately excluded from the tenant-blind engine catalog (the cross-tenant bug class).

Mapping to your ops world
