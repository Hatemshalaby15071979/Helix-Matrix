Lesson 0002 — Event sourcing vs. "just log it"

Primary source: Martin Fowler — Event Sourcing.

Why this lesson

In ops you keep audit trails: who changed a schedule, when, why. "Just log it" captures the fact of change but loses the intent and the sequence. Event sourcing treats every state change as an immutable event; current state is a projection of the event stream. The audit trail becomes the source of truth, not a side-effect.

Concept

  • Event: an immutable record of something that happened ("ShiftAssigned", "KPIThresholdBreached"). Past tense, factual, never edited.
  • State: derived by replaying events in order. Delete the database and you can rebuild state from the log.
  • Projection: a read-optimised view (e.g. "current schedule") computed from events. Multiple projections from one stream.
  • Snapshot: a cached projection to avoid replaying from zero on large streams.

Contrast with CRUD: in CRUD you overwrite state and the "why" is gone. In event sourcing the "why" is the data.

Mapping to your ops world

Ops realityEvent-sourcing pattern
Schedule change log (who/when)Event stream "ShiftAssigned" with actor + timestamp
Re-running a KPI report for last monthReplay events up to date X → projection at that date
"What did the forecast say on Tuesday?"Temporal query on the event stream
A bad edit you can't undo cleanlyAppend a compensating event; history stays honest

Helix's implementation

Helix keeps an append-only, hash-chained audit_events ledger: every governance decision is written before it runs. Combined with event-sourced memory, any action is replayable and inspectable — the "evidence before claims" principle in code.
